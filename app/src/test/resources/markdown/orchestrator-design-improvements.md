# L1向けオーケストレーター設計改善策

作成日：2026-10-31 / 版：1.1

## 1. 目的と適用範囲

L1メインセッションが、生成前に組織・権限・成果の流れを設計するための指針。暗号資産模擬売買による構成評価のログを根拠とするが、原則は他の開発・調査タスクにも適用できる。

対応する生成用規約は `RULE.md`。いずれも設計用文書であり、保存だけで自動適用・起動・権限付与されるものではない。AGENTS.mdやアプリの権限より優先しない。

## 3. 最重要の変更：L1が「人数」より先に「成果経路」を設計する

生成前に次の順で決める。

1. **最終成果**：利用者が何を使い、どの結果を見たら成功か。
2. **最小の縦断経路**：入力→処理→出力→検証までの最小単位。
3. **依存DAG**：何が何を待つか。最短経路と独立作業を分ける。
4. **部門境界**：連携が密な作業を同じ部門に置く。
5. **権限と検収**：誰が誰の成果を承認するか。
6. **担当数・モデル・並列数**：実際に分離できる作業量から決める。

模擬売買なら、初回は「一つの公開データ源、一銘柄、一戦略、単一書込台帳、結果集計、読み取り画面、独立照合」を成立させる。複数銘柄・複数トレーダーの追加は、その後の別マイルストーンとする。実行条件は利用者の承認範囲を守り、未承認の数値を埋めない。

## 4. 推奨レイアウト：部門検収を下位へ委任する

```text
L1 利用者窓口：目的・構成案・承認事項・最終説明
└─ L2 Commander：部門間調整・全体計画・部門成果受入
   ├─ L3 開発マネージャー
   │  ├─ L4 データ接続
   │  ├─ L4 エンジン/業務ロジック
   │  ├─ L4 台帳・集計
   │  └─ L4 Web表示
   ├─ L3 運用/トレーディングマネージャー（必要になった段階で）
   │  └─ L4 実行担当群
   ├─ L3 Evaluation：独立した結果照合
   ├─ L3 Security：安全性の独立判断
   └─ L3 Risk：必要な案件で条件・リスクの独立判断
```

これは生成済み構成ではなく設計例。分野に不要な部門は作らない。1人で完了する作業に専任マネージャーは通常不要。Security/Riskはこの評価案件の合意を継承した例であり、すべての案件に無条件で同じ役職を要求する趣旨ではない。

### 部門を分ける基準

- 複数担当の共通仕様・結合・検収が繰り返し必要ならマネージャーを置く。
- 部門成果が独立に受入可能で、責任境界を説明できること。
- 当面の設計目安はCommanderが直接管理する成果単位を3〜5に抑える。アプリ上限でも実測最適値でもない。実行後の待ち時間で調整する。
- いきなり全専門職へ上司を付けず、今回ならまず開発部門をまとめる。
- 既存セッションの親子関係を手動ファイル移動で変更しない。再配置の可否は管理APIで確認し、対応機能がなければ新構成案を示す。不要な削除・再作成を勝手にしない。

### 検収責任

| 層 | 検収対象 | 原則として繰り返さないこと |
|---|---|---|
| 部門マネージャー | 個別実装、単体テスト、部門内結合、修正結果 | 全件をCommanderへ丸投げ |
| Commander | 部門の合格証拠、部門間契約、全体結合、未解決事項 | 毎回すべてのソースを最初から読む |
| 独立評価者 | 生の入力・実行結果と計算の照合 | 作成部門の自己合格を流用 |
| L1 | 利用者の目的・承認条件・最終結果との一致 | 日々の部門内差戻しを指揮 |

部門マネージャーを単なるPlannerにしない。委任範囲内の子課題について詳細検収・修正を完結させる。実際の管理操作はアプリが認めるmanager関係と担当範囲に限定する。対応できない操作は権限を創作せず上位へ限定エスカレーションする。

## 5. 「最終結果だけ報告」ではなく「集約結果＋例外通知」

通常の部門内会話・逐次ログはCommanderに流さない。SQL資産に詳細を残し、以下だけを上げる。

| 通知 | 必須内容 |
|---|---|
| 部門成果完成 | 成果版、合格証拠、検収者、制約、次工程 |
| 引渡し準備完了 | 使用可能な入出力契約・資産版、受取担当 |
| ブロック | 原因、止まる範囲、必要な判断、継続可能な並行作業 |
| 重大変更 | 目的・安全・費用・期限・部門間契約への影響 |

通知を減らすことと証拠を隠すことは別。Commanderと独立評価者は認可された証拠へ追跡できなければならない。完了まで沈黙して仕様不一致を抱え込む構成にしない。

## 6. 共通契約と実行担当を生成時に固定する

部門間契約には、少なくとも次を含める。

- schemaVersion、作成者、利用者、データ型、必須項目、単位、UTC規則。
- 欠測/nullと実際の0の区別、非有限数、異常入力、失敗時の状態。
- 入力資産ID/取得revision/ハッシュ、出力資産、互換性方針。
- データ源・対象・実行モード、読み書きの所有者、結合テスト。

初期契約の合意だけを直列工程にし、合意済み境界の内側を並行開発する。部品が公開された時点で増分結合し、全員の完成を待たない。仮の設計書との一致だけで互換性を合格にしない。

信号生成、設定統合、実行ループ、エラー回復、結果集計、Web更新など、部門の隙間の機能にも必ず一人の責任者を割り当てる。複数担当で共有台帳へ同時書込みする設計は、排他制御なしに採用しない。

## 7. 実行と審査のゲートを分ける

1. ユーザー承認：範囲・必要条件・副作用。
2. 事前適合性：設定・実装・安全境界。
3. 実行：承認範囲のデータ取得や模擬処理。
4. 事後評価：実結果・損益・整合・構成連携。

事後評価PASSを初回実行の必須入力にしない。必要なら事前テスト判定を別のdecision型として定義する。未設定条件がある場合は利用者が選べる最小案を一括提示し、影響のない実装や安全な単体テストは続ける。既存の開始指示を無視した再承認を連発しない。

今回のSecurity所見には具体的なファイル境界・資源制限の欠陥があった。確認の全廃ではなく、実行を止める本質的欠陥と後で改善できる事項を分ける。

## 8. 変更・証拠・状態の管理

- 一つの版付き構成manifestを正本にし、役割・人数・親子関係・モデル・担当・承認範囲・並列数を整合させる。
- 新方針ごとに許可事項と禁止事項の差分をまとめる。軽微な変更だけで無用な全体replanをしない。
- replanで未完了旧版が中断される場合は影響を説明し、旧成果を明示再検証して使う。黙って新しい成果に見せ替えない。
- report公開時にrunId/planRevision/itemId/taskId/commandId/取得可能なexecutionIdを関連付ける。識別子はAPI応答を使い、未知は未知とする。
- ソースあり、構文成功、単体成功、結合成功、実行済み、独立検証済み、manager受入済みを別に記録する。
- 操作カード、手動プロセス、health、PID、停止方法を区別し、停止対象を利用者へ明示する。

## 9. 次回の比較評価

並列上限は既存アプリ上限8以内、資源に応じて設定する。階層を増やしても全体上限が部門数倍になるわけではない。利用可能なモデルは対象別に検索し、部門マネージャーを含め表示名からIDを推測しない。

次の指標で「フラット構成」と「部門制」を比較する。目的・環境が異なる場合は単純比較しない。

| 指標 | 定義 |
|---|---|
| 最小縦断完了時間 | 合意済み開始点から最初の有効な一連結果まで |
| 検収待ち時間 | 成果提出からmanager判定まで。中央値・上位分位も取る |
| 依存解除待ち | 前提がそろってから着手まで |
| L2管理負荷 | L2判定件数、詳細再読件数、介入回数、取得できる場合のコスト |
| 手戻り | 差戻し理由別件数、旧版化件数、再利用の成否 |
| 連携 | 入出力不一致、アクセス拒否、引渡し完了/対象件数 |
| 稼働 | 実測同時実行数。設定上限を実績としない |
| 信頼性 | 未実施を成功表示した件数、再現可能性、停止漏れ |

イベントの時刻・分母・欠測を保存する。AIによる進捗ポーリングで計測しない。今回の分析だけから改善率や最適人数を数値保証しない。

## 11. 一般的な最適化の統合要約（プロンプト用）

以下を設計指示として使用する。今回のログで直接実証した改善と、一般的な設計原則を混同しない。最適人数・階層・モデルや速度向上率は実測で判断する。

1. **目的と構成選択**：品質・所要時間・コスト・信頼性の優先順位と許容範囲を最初に定める。短く密結合な作業は単一AI＋ツール、少数の独立作業は中央管理、調整・検収の多い大規模作業は部門制、手順が確定した反復処理は固定ワークフローを選ぶ。マルチエージェントや階層化自体を目的にせず、管理・通信の追加費用も評価する。
2. **DAGとクリティカルパス**：最終成果までの依存DAGを作り、完了を支配する経路を優先する。最小縦断経路を先に動かし、独立作業だけを並行化する。部門マネージャーに詳細検収を委任し、Commanderは部門間調整と部門成果受入へ集中する。上位で全件再検収して階層化の効果を消さない。
3. **機械的処理の非LLM化**：必須field/JSONスキーマ、hash/版/実行ID、テスト成否、依存解除、再試行回数・期限、状態集計、重複防止は可能な限り通常コードで検査・制御する。曖昧な判断のみLLMへ渡す。検査コードの実装・正しさも検証し、自動判定を権限やユーザー承認の代用にしない。
4. **コンテキストと通信**：担当に必要な情報だけを渡し、共通仕様と大きい成果は版付き参照にする。通常は短い要約＋根拠の参照、必要時のみ認可された詳細を読む。制約・版・未解決事項を要約から落とさない。通知は完成・引渡し・ブロック・重大変更に集約し、詳細証拠は保持する。全履歴の一斉配布やAIによる進捗ポーリングをしない。
5. **モデルルーティング**：抽出/分類/整形は軽量・低遅延、明確な実装は実装性能と費用、複雑な計画/原因分析は推論能力、重要な検証は必要な能力を基準に選ぶ。承認範囲内で低コスト処理から始め、失敗・曖昧さ・重大性に応じて強いモデルへエスカレーションする。明示されたモデル指定を無断変更せず、対象別カタログで正式IDを確認する。モデルを分けるだけで独立性を保証せず、生の証拠と独立テストで検証する。
6. **動的並列度とバックプレッシャー**：APIレート、CPU/メモリ、費用、外部応答、下流の検収待ちに合わせて投入を調整する。下流が詰まったら上流の新規投入を抑え、依存解除・統合を優先する。全体上限8を守り、単なる負荷調整のたびに無用なreplanをしない。利用可能なスケジューラ機能で対応できない場合は制約を明示する。
7. **障害回復と上限**：一時的通信障害等の再試行可能な失敗と、権限/仕様不一致等の設計修正を分ける。必要に応じ待ち時間を延ばし、一時失敗だけを限定再試行する。副作用は冪等性キー・実行記録で二重実行を防ぐ。版/設定/入力hash付きチェックポイントから、互換性を確認して失敗した工程だけ再開する。再試行回数・時間・費用・修正反復に上限を設け、改善しなければ原因と選択肢を上位/人へ戻す。
8. **段階検証と早期終了**：安価な形式検査→単体→結合→実結果照合→必要な専門家/人の判断の順に検査し、明白な不備は早期に差し戻す。リスクに応じ検証の重さを選び、必須の安全確認は省略しない。合格条件を満たした成果には不要な再レビュー・際限のない改善を追加せず、必要なmanager受入を終えて終了する。
9. **実測による選択**：同じ課題・合格条件・承認範囲・近い環境/予算で単一AI、フラット、階層構成を比較する。品質/成功率、最終完了時間、トークン/実行費用、作業/検収/依存待ち時間、引渡し/結合失敗、差戻し、人手介入を測る。計測不能は未知として記録し、品質や安全を下げた高速化を成功としない。測定結果から人数・階層・モデル・同時実行数を調整する。

### プロンプトへの適用方法

`RULE.md` の「生成用統合プロンプト」をコピー用の要約正本とし、本節と既存のログ分析・権限・来歴・停止規約を合わせて運用する。コピー先にもAGENTS.mdと権限が優先することを明記する。要約だけで今回の実行条件や権限が承認されたと解釈しない。

## 12. 導入順

まず設計レビューでこのチェックリストを使い、開発部門の詳細検収を委任する。次に最小縦断経路を検証し、必要になった段階で運用部門を拡張する。既存の停止済みチームを自動移行・再起動することは、この文書の作成に含まれない。
